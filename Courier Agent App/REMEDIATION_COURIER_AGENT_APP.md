## 3. Retry-with-backoff in ApiClient before ErrorView

**Status:** ✅ Done

**Files:**
- `lib/services/api/api_client.dart`

**What changed:**
- `_run()` now retries up to `maxAttempts = 3` times (1 initial + 2 retries)
  with exponential backoff (300ms, then 600ms) on `TimeoutException`,
  `SocketException`, and `http.ClientException` — the same transient-failure
  set and backoff schedule as `Hill Go Main Customer App`'s `ApiClient._send`.
  Every request is now wrapped in a 25s timeout via `.timeout(...)`.
  Attempts and the final failure are logged through `AppLog.w`/`AppLog.e`.
- HTTP error *responses* (4xx/5xx) are decoded and thrown immediately — no
  retry — so validation errors (e.g. wrong OTP) still surface instantly.
- Only after all attempts are exhausted does the call throw
  `ApiException(0, 'Cannot reach the HillGo server...')`, which is what
  providers turn into the `error` state that `ErrorView` renders. So retries
  now happen *before* any `ErrorView` is shown, per the checklist wording.
- Public API of `get`/`post`/`patch`/`multipart` is unchanged (only new
  optional named params were added — see item 7).

**How verified:** `flutter analyze` clean. Code review confirms the retry
loop mirrors the Customer App's proven implementation. Full network-failure
injection wasn't exercised (would need a fake `http.Client` swapped into
`ApiClient`, which the class doesn't currently support without changing its
constructor signature — out of scope to avoid touching the public
constructor); behavior was verified by reading the control flow and running
the full existing test/analyze suite to confirm no regressions.

## 8. Wire language preference into real UI localization

**Status:** ⚠️ Partial (infrastructure complete; full string translation out of scope)

**Files:**
- `pubspec.yaml` (added `flutter_localizations` from the Flutter SDK)
- `lib/services/locale_controller.dart` (new)
- `lib/main.dart` (`MaterialApp.router` now sets `locale`, `supportedLocales`, `localizationsDelegates`; locale seeded at boot from the signed-in user's saved language)
- `lib/screens/profile/language_screen.dart` (selecting a language now also updates `LocaleController`, not just the backend preference)

**What changed:**
- (a) Added `flutter_localizations` and wired
  `GlobalMaterialLocalizations.delegate`, `GlobalWidgetsLocalizations.delegate`,
  `GlobalCupertinoLocalizations.delegate` plus
  `supportedLocales: [Locale('en'), Locale('bn')]` on `MaterialApp.router`.
- (b) `_bootstrap()` in `main.dart` seeds a `LocaleController` from
  `authProvider.user?.language` (the same field `UserModel.language` /
  `PATCH /courier/settings` already populate) immediately after session
  restore, before the first frame.
- (c) `LocaleController` (`ChangeNotifier`) holds the active `Locale`;
  `HillGoApp` watches it via `provider` and passes `locale:
  localeController.locale` into `MaterialApp.router`, so calling
  `setFromLanguageCode('bn')` triggers a full rebuild with the new locale.
  `LanguageScreen`'s tap handler now calls both
  `profile.updateLanguage(code)` (persists to the backend, unchanged) *and*
  `context.read<LocaleController>().setFromLanguageCode(code)` (switches the
  app locale immediately, no restart needed).
- **What is *not* included:** a full ARB/`.arb` translation table for the
  app's own copy (button labels, screen titles, etc.). Flutter's built-in
  Material/Cupertino/Widgets locale data (date formats, default dialog
  button labels, text-field context menus, etc.) genuinely switches between
  `en`/`bn` now; the courier-specific strings in each screen remain
  hardcoded English, same as before. This matches the checklist's explicit
  allowance to document a partial pass when full ARB tables are
  time-constrained — the locale itself does actually switch and persist
  across restarts, which was the hard requirement.

**How verified:** `flutter analyze` clean, `flutter test` passes.
`flutter pub get` resolved `flutter_localizations` from the SDK. Verified by
reading `MaterialApp.router`'s resolved `locale` argument path and
`LocaleController`'s `ChangeNotifier` wiring; no dedicated widget test was
added for locale switching since it requires pumping the full `HillGoApp`
with routing/providers, which is out of scope for this pass's test additions
(item 1 already covers the app's testable business logic).
