## Vendor / Merchant App
Observed while remediating `AUDIT_VENDOR_MERCHANT_APP.md` (2026-08-03). Not fixed — out of the 10-item checklist scope.

- **Single orders endpoint mixes active + history.** `GET /merchant/orders` (used by the new paginated `OrdersProvider.loadMoreHistory`) returns all statuses together, newest first. "Load Older Orders" on the History tab therefore pages through the same endpoint as active orders rather than a delivered-only feed. A dedicated `status=delivered` filter or endpoint (server-side) would make history pagination and page-size expectations cleaner and avoid active orders occasionally showing up mid-page during "load more".
- **Redundant double-polling when both Home and Orders tabs have been visited.** `MainShell` uses `go_router`'s `StatefulNavigationShell`, which keeps branch state alive (`IndexedStack`-style). Since both `HomeScreen` and `OrdersScreen` now each run their own independent `Timer.periodic(8s)` calling `OrdersProvider.refreshSilently()` (per checklist item 4, which named both locations), once a merchant has visited both tabs at least once, two independent 8s timers keep running concurrently (harmless — idempotent GETs — but doubles background poll traffic). A shared single timer (e.g. owned by `OrdersProvider` itself, started/stopped via a listener-count) would be more efficient.
- **`getMePrefs()` and `getStore()` in `StoreProvider.load` are still sequential.** Checklist item 6 only named `reviews/payouts/transactions/revenue` for parallelization; these two earlier calls are independent of each other (both only depend on the auth token, not on each other's result) and could also run via `Future.wait`, shaving a bit more time off the dashboard's time-to-interactive.
- **Order mutations (`accept`/`reject`/`markReady`/`markDelivered`) don't send an idempotency key.** Now that `ApiClient` retries transient network failures (checklist item 3), a POST whose *response* was lost to a timeout (but which the server actually processed) could be retried and reach the server twice. The Customer App's `ApiClient.newIdempotencyKey()` + `Idempotency-Key` header pattern (`Hill Go Main Customer App/lib/services/api/api_client.dart:113-134`) isn't ported to the Vendor app; wiring it into the order-action endpoints would close this gap. (Retries only happen for network-level failures before a response is received, so this is a narrow window, not a new regression, but worth flagging now that retries exist.)
- **Dependency staleness.** `flutter pub get` reported 58 packages with newer versions incompatible with current constraints (e.g. `go_router` 14.8.1 → 17.3.0 available, `fl_chart` 0.70.2 → 1.2.0 available, `flutter_secure_storage` 9.2.4 → 10.3.1 available). Not touched — upgrading transitively-pinned majors is a separate, riskier effort outside this checklist.
- **Products/categories lists still use a hardcoded `per_page: 50` with no pagination** (`api_product_repository.dart`). Checklist item 10 only scoped order history pagination; a merchant with >50 products or categories would still only see the first page with no "load more" affordance.

## Public Web
Observed while remediating `AUDIT_PUBLIC_WEB.md` (2026-08-03). Not fixed — out of the 7-item checklist scope.

- **No rate limiting / CSRF / auth on any `/public/*` endpoint from this tree.** Confirmed (again) at remediation time: `Hill Go Public Web` has no server code at all — all rate limiting, CORS allowlisting, and anti-automation controls for `track`, `quotes`, `availability`, `newsletter`, `contact`, and `partner-applications` must live in `hillgo-backend`. Worth a dedicated pass there (e.g. is `/public/newsletter` rate-limited per IP to prevent list-bombing? is `/public/contact` rate-limited to prevent spam?) since the retry-with-backoff added in this pass (checklist item 5) means a flaky client network can now generate up to 3x the request volume per user submission than before.
- **`npm audit` reports 5 vulnerabilities (3 moderate, 1 high, 1 critical) in the new `vitest` devDependency tree** (transitive, via `esbuild`/`vite`). This only affects the local test-runner toolchain — `vitest` and its dependencies are never shipped to the static site (no `<script>` tag references anything under `node_modules`, and `node_modules/` is already covered by the repo-root `.gitignore`) — but it should be tracked and periodically bumped (`npm audit fix` / `npm update vitest`) since it's now a permanent part of the repo's dependency surface.
- **`js/config.js`'s `window.HILLGO_API_BASE = window.HILLGO_API_BASE || ''` pattern only works if nothing overwrites the global after `config.js` runs but before `api.js` reads it.** This is fine given the current fixed 3-script load order (`config.js` → `api.js` → `main.js`), but there's no runtime guard (e.g. `Object.freeze` or a setter) preventing a future script tag from being inserted between them and clobbering the value. Not fixed here since it would mean adding defensive code with no current caller that needs it — flagging for awareness if more scripts are added to these pages later.
- **`css/style.css` was not audited line-by-line for CSP `style-src` reduction opportunities.** The remediation kept `'unsafe-inline'` for `style-src` (matching the Admin Panel's own CSP and required by the many existing inline `style="..."` attributes across all 14 pages), but a follow-up pass could move the highest-traffic inline styles (e.g. the repeated hero/section inline positioning in `index.html`) into `css/style.css` classes, which would let a future CSP drop `'unsafe-inline'` from `style-src` entirely. Out of scope for this checklist, which only asked for a "reasonable" CSP with `'unsafe-inline'` explicitly allowed "if needed for existing inline styles."
- **`services.html`'s "Trusted by Industry Leaders" and `index.html`'s "Powering the Ecosystem with Global Leaders" sections list fictional company names** (`TECHCORP`, `GLOBEX`, `SKYNET`, `UMBRELLA`, `CYBERDYNE`, `SOYLENT`, `SECURE LOGISTICS`, `VELOCITY CORP`, `NEXUS CLOUD`, `GREEN MOTION`). This is a placeholder-logo-wall pattern, not a fake precision/stat claim like the checklist's item 7 (99.9%/12ms), so it wasn't touched — but it's the same general "unsubstantiated trust marketing" category and a reviewer may want it addressed in a future pass (e.g. swap for a generic "and 3,000+ businesses nationwide" phrasing, consistent with `index.html`'s own real "Trusted by 3000+ Merchants" section just above it).
- **`index.html`'s own `why-stats` block (`99.9% Safe Trips`, `24/7 Live Support`, `100% Verified`) was intentionally left untouched** — see REMEDIATION_PUBLIC_WEB.md item 7 for why (different claim category than the checklist's named `services.html` figures); logging it here explicitly so it isn't mistaken for an oversight.

## Admin Panel
Observed while remediating `AUDIT_ADMIN_PANEL.md` (2026-08-03). Not fixed — out of the 10-item checklist scope.

- **Queue screens (KYC / onboarding) still render every row with no pager, even though their store.js loaders are now paginated.** Checklist item 7 named "customers, rides, etc." as the large collections to add server pagination to; `riderKyc`, `courierKyc`, and `merchantOnboarding` got the same `pagedLoader('/admin/.../kyc', ...)` treatment in `store.js` (for consistency and so `AppStore.loadMore()` works on them too), but their page renderers (`js/pages/rider.js#riderKyc`, `js/pages/courier.js#courierKyc`, `js/pages/merchant.js#merchantOnboarding`) never called `UI.paginate()`/`UI.pagerHtml()` to begin with and still don't — they map the full in-memory array. If any of these queues exceeds 50 pending items, the admin only ever sees the first server page with no "Load more" affordance on screen (though `AppStore.loadMore('riderKyc')` etc. would work if wired up). A follow-up UI pass should add the same pager + `bindServerMore()` pattern used on the customers/riders/merchants tables.
- **`merchantPayouts` and `courierWithdrawals` list pages have no client-side pagination at all** (`js/pages/merchant.js#merchantPayouts`, `js/pages/courier.js#courierWithdrawals`) — they render every row from `state.merchantPayouts` / `state.courierWithdrawals` directly. Their store.js loaders are now paginated (capped at the first server page of 50), so a shop with >50 payout/withdrawal records will silently only ever show the first 50 with no indication more exist. Same fix as above (add `UI.paginate()` + pager + `bindServerMore()`) would close this; left out because the checklist's "at minimum" wording scoped the UI wiring to the tables that already had a pager (customers, rides, riders, trips, merchants, merchant orders, courier agents, courier parcels).
- **`activityLog` and `pricingAudit` loaders remain uncapped / unpaginated** (`get('/admin/activity')`, `get('/admin/pricing-audit')` with no `per_page`). Not part of the checklist's named "large collections," but on a long-lived admin tab with heavy activity these could grow into large single-response payloads over time. A dedicated `per_page`/cursor on those two endpoints would be a natural follow-up once the backend ships item 7's pagination work generally.
- **Retry-with-backoff (checklist item 3) covers all `http()` callers uniformly, including non-idempotent POST mutations** (e.g. `POST /admin/customers/:id/wallet`, `POST /admin/riders/kyc/:id/status`, `POST /admin/courier/incentives/:id/toggle`). Retries only fire on a transient *network* failure before any response is received (never on a definitive 4xx/5xx), so the window for a request reaching the server but its response being lost is narrow — but if it happens, the retry could resubmit the same mutation a second time (e.g. double wallet adjustment). The Vendor/Courier apps' `Idempotency-Key` header pattern isn't ported here; adding one to `http()` for POST/PATCH/PUT and having the backend dedupe on it would close this gap. Flagged, not fixed — outside the "retry with backoff" checklist wording, which only asked for the retry behavior itself.
- **Sentry CDN version is pinned inline in `js/telemetry.js` (`7.120.0`).** Fine for now (Sentry loads dynamically only when `window.SENTRY_DSN` is set, so unconfigured deployments never fetch it), but like the Public Web `vitest` pin, it should be revisited periodically rather than left indefinitely.
- **CSRF protection remains unimplemented** (Bearer-token SPA pattern, no CSRF tokens) — unchanged from the audit; checklist item 6 only asked for CSP script-src hardening, not CSRF, and item 5 already tracks the broader token-storage posture as an accepted/blocked risk.
